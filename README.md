# 鸣潮·无音消除 助手

读屏识别棋盘 → 计算最优交换 → 提示或自动执行。适配 3840×2160 全屏、8 列 × 7 行。

**必须以管理员身份运行**：鸣潮以管理员启动，Windows 的 UIPI 会静默丢弃低权限进程
注入的鼠标事件（函数返回成功、光标也动，但游戏毫无反应）。

---

## 下载

直接用打包好的 exe，去 [Releases](https://github.com/a1oyss/wuwa-elim/releases) 下最新的
`wuwa-elim-<版本>-<commit>-win64.zip`，解压后里面就是全部东西。

包名、exe 名、窗口标题栏、日志首行都带着**版本 + git commit + 打包时间**，
所以拿到手就能确认是不是最新版；对不上就是旧包，重新下一份。

## 快速开始（给使用者）

1. 打开游戏，进入【无音消除】，停在能看到棋盘的界面。
2. 双击 `无音消除助手-<版本>-<commit>.exe`，UAC 弹窗点【是】。
3. 界面出现：
   - **识别一次** — 只读屏，在右侧给出这一步该怎么拖
   - **开始自动** — 自动执行，每步重新截图重新计算
   - **停止** / 键盘 **F8** — 随时中断

   快捷键：**F5** 识别一次、**F6** 开始自动、**Esc** 停止。

4. 窗口会自动避开游戏所在的显示器（有多屏时放到另一块屏），
   没有第二块屏时才会置顶并压在全屏游戏上。
   无论哪种情况，都别让它盖住棋盘。

日志在 `%LOCALAPPDATA%\WuwaElim\logs`，界面右上角【日志】按钮可直接打开。

## 从源码运行

```powershell
py -3.14 -m pip install -e .
py -3.14 -m wuwa_elim          # 图形界面
py -3.14 -m wuwa_elim.cli      # 命令行，只提示不动手
py -3.14 -m wuwa_elim.cli --run --loop 20   # 自动连打
```

命令行常用参数：

| 参数 | 说明 |
|---|---|
| `--run` | 真的执行（默认只提示） |
| `--loop N` | 连续执行 N 步 |
| `--top N` | 打印前 N 个候选 |
| `--mode drag\|click` | 拖拽 / 点两下 |
| `--log NAME` | 同时写日志到 `%LOCALAPPDATA%\WuwaElim` |

## 打包

```powershell
powershell -ExecutionPolicy Bypass -File packaging\build.ps1
```

产物（名字里带版本和 commit，旧包一眼就能认出来）：

- `dist\无音消除助手.exe` — 单文件、无控制台、双击即请求管理员权限
- `dist\wuwa-elim-<版本>-<commit>\无音消除助手-<版本>-<commit>.exe`
- `dist\wuwa-elim-<版本>-<commit>-win64.zip` — 含 exe、README、使用说明、build-info.json

`uac_admin=True` 写在 `packaging/wuwa_elim.spec` 里，所以双击就会弹 UAC；
`console=False` 保证不出现黑窗口。

### 构建身份

`build.ps1` 会把 `__version__` + git 短 SHA + 打包时间写成 `packaging/build-info.json`
并随包打进 exe（`wuwa_elim.version.describe()` 负责读）。于是：

- 标题栏显示 `鸣潮·无音消除 助手  v1.2.0 · d16113a · 2026-11-04 21:30`
- 日志第一行同样打印版本
- 未提交的改动会带 `-dirty` 后缀
- 脚本还会核对 `__version__` 与 `pyproject.toml` 是否一致，并在打包完成后检查
  "有没有源文件比产物新"——这两条都是为了杜绝"代码更新了，包还是旧的"

源码运行时没有 build-info.json，版本显示成 `1.2.0（源码）`。

### 图标

图标**直接取自游戏画面**：截一张图，按 `packaging/make_icon.py` 里的 `CROP`
框取人物头部，圆角裁切后输出多尺寸 ico。不重绘、不抠图，保证和原画一致。

```
py -3.14 packaging/make_icon.py            # 从当前游戏窗口取图
py -3.14 packaging/make_icon.py 截图.png    # 从已有截图取图
```

产物同时写到 `packaging/app.ico`（打包用）和 `src/wuwa_elim/assets/`
（运行时用）。后者会随 exe 一起打包，主题栏/任务栏的图标由 `ui.py` 的
`_apply_icon()` 在启动时设置 —— **只嵌 EXE 图标是不够的**，运行中的窗口默认
仍是 Tk 的羽毛图标。

> 打包入口必须是 `packaging/launch.py`（绝对导入），**不能**直接拿
> `src/wuwa_elim/__main__.py`：PyInstaller 把入口脚本当独立脚本分析，
> 里面的相对导入解析不了，整个 UI 分支（含 tkinter）都不会被打进包里。

## 规则

交换相邻两格，若某行或某列出现 ≥3 个同类就消除得分；消除后上方棋子下落，
顶部补新的随机棋子。**冰块挡住的地方补不进来**：冰块在顶行时，这一列消空的部分
会一直留着，成为真正的空位。

| 棋子 | 生成条件 | 外观 | 效果 |
|---|---|---|---|
| 爆炸 | 直线消除 4 个 | **保留原颜色**，四**角**黄三角 | 被消除时炸掉周围 3×3 |
| 十字 | T 形或 L 形消除 5 个及以上 | **保留原颜色**，上下左右四**边**黄三角 | 被消除时清掉同行同列 |
| 终极 | 直线消除 5 个及以上 | 粉色棋盘格，无颜色 | 与任意棋子交换清除全盘同类型；两个终极交换清空全盘 |
| 冰块 | 棋盘固有 | 青色方块 | 不可移动、不下落，挡列；周围完成一次消除时碎。顶行的冰块还堵住补充口 |
| 能量瓶 | 棋盘固有 | 紫瓶 + 头顶 1~3 金心 | 周围完成三次消除后消失，给角色 80 能量 |
| 沙漏 | 第五关目标 | 金色沙漏 | 不参与三连、不被爆炸波及；随重力下落，**触底自动消失并 +2 操作回合** |
| 空位 | 顶行冰块那列消空之后 | 什么都没有，就是槽底 | 不算棋子：不能交换进去、连不成三连，但会被动等上面的棋子落下来填 |

**爆炸/十字是带颜色的棋子**，能参与三连，靠"被消除"触发。

**沙漏关的排序偏向送沙漏下落**：触底一颗按等效 20 格计分、每往下落一行再给一点
小奖励，所以引擎会优先消沙漏下面的棋子，而不是只顾眼前分数。这两项只影响排序，
不进预测分数。

### 棋子编码

| 编码 | 含义 |
|---|---|
| `G R M D L` | 五种可消除颜色 |
| `Gb` `Gx` | 同色棋子 + 爆炸 / 十字标记 |
| `u` | 终极棋子 |
| `C` | 冰块 |
| `O3` `O2` `O1` | 能量瓶（后缀 = 剩余心数） |
| `H` | 沙漏（第五关目标，触底消失 +2 回合） |
| `?` | 未识别（当墙） |
| `.` | 空位（顶行冰块挡住补充时留下） |

## 容错

三步之间棋盘的动画会让读数不稳定，所以每一步都按"稳定"来判断：

1. 连续两次读数完全一致
2. 未识别格 = 0

不满足就每 0.35s 重读，最多 12s。

> "未识别"只算 `?`。顶行有冰块的那一列补不进新棋子，消完会留下空位 `.`，
> 那是棋盘本来的样子，不是没认出来。以前一起算成 `?`，结果这种盘面每一步都
> 判不稳，日志刷满"有 1 格没认出来"，直到重试次数耗尽才停。
> 区分靠像素本身：空位就是槽底背景（实测 rgb 46,37,58、亮点占比 0.00），
> 而弹窗把整屏压暗时棋子仍然带颜色（离背景 >60），不会被误判成空位。

"盘面上还有三连"只作为动画未结束的提示，**不**当硬条件 —— 一旦某格被认错，
会永远等不到"无三连"而卡死（终极棋子被认成白兔时就是这么卡住的）。同样的状态
持续超过 4 秒，判为识别误判并继续。

点击后的验证：`wait_effect()` 要求盘面**至少变 2 格**。

> 一开始用的是"有没有变化"，结果实测 6 步里只有 4 步被游戏接受，日志却全报"生效"。
> 原因是上一步的连锁会延迟补下一颗棋子，那一格的变化被误判成生效。真实的一步至少
> 消掉 3 个棋子，所以拿 2 格当门槛就能挡掉这种假信号。

没生效就重试，且**重试前重新读盘重算**，不用过期走法。

## 识别标定

最近邻分类用的是实测中心均色，几个易混项单独加判据：

- **终极棋子**：品红像素占比（实测 0.248；真白兔 0.012），阈值 0.15
- **爆炸 / 十字**：黄色小三角是否在四角 / 四边**对称**出现，
  单块区域黄色占比门槛 0.045
  （实测爆炸四角最小 0.077、十字四边最小 0.089、普通棋子 0.000~0.010）
- **暗色格子**：亮度 < 0.45 直接判未识别，避免深色特殊图标被认成普通颜色

换分辨率或重新标定：

```powershell
py -3.14 -m wuwa_elim.tools.probe          # 看窗口/显示器
py -3.14 -m wuwa_elim.tools.analyze        # 画网格叠加图，确认对齐
py -3.14 -m wuwa_elim.tools.marker_probe   # 打印每格四角/四边黄色占比
```

再改 `src/wuwa_elim/constants.py` 里的 `BOARD_ROUGH`、`CALIB_*`、`TILE_COLORS`、`ZONE_MIN_FRAC`。

## 还没确认的地方

1. **长连奖励和连锁倍率**未实测。`per_tile=10` 是实测值（消 6 个得 60 分），
   另外两项是占位，只影响排序。
2. **终极棋子的"同类型"**：说明写的是"消除棋盘上同类型棋子"。终极本身无颜色，
   引擎按"清除**被交换那一格**的颜色"建模。若实际按隐藏颜色算，估值会偏，
   但走法仍合法。
3. **特殊棋子落点**：假设生成在玩家刚动过的那一格（否则放连串中间）。实测爆炸
   生成后会被后续下坠带走，所以位置对不上是正常的 —— 下一次读数由黄三角识别回来。
4. **两格预判**没有，目前是贪心：只看这一步及其连锁。

## 踩过的坑

- **DPI**：进程必须声明 DPI 感知，否则 150% 缩放下窗口坐标是逻辑像素，
  和真实屏幕像素差 1.5 倍。
- **UIPI**：游戏提权运行时，低权限进程的 `SendInput` 会被静默丢弃。
  表现和"游戏有反作弊"一模一样，实际是权限不一致。
- **网格拟合**：相位不能用缝隙色（方块边缘阴影会造出假缝，整列偏 1/3 格），
  要用亮像素投影。另外弹窗压暗画面时拟合会跑偏（出现过 11×9），
  所以结果必须校验，不合理就退回标定值。
- **相对导入打包**：见上文"打包"一节。
- **重命名方法漏改调用点**：把 `_busy` 改名成 `_set_busy` 时，两个工作线程里还留着
  `self._busy(...)`。线程一启动就 `AttributeError` 死掉，而**线程异常不会显示在界面上**，
  表现就是"点了按钮完全没反应"——日志里连一条记录都没有。
  现在给工作线程套了统一的兜底：任何异常都会被写进日志，不会再静默失败。
  排查这类"点了没反应"时，先看 `%LOCALAPPDATA%\WuwaElim\logs` 里有没有
  `工作线程异常`。
- **Tk 的负数坐标不是坐标**：`geometry("1000x900-1040+753")` 里的 `-1040` 表示
  "距右边缘 1040 像素"，不是 x = -1040。多屏时左侧副屏的坐标是负的，用 geometry
  会把窗口丢到主屏右侧去。窗口定位统一改用 Win32 `SetWindowPos` 做绝对坐标。
